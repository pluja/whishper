# Contributing

Thanks for helping with Anysub. This page covers the layout, conventions, and checks. [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) explains how the system fits together and why. Report security problems through [SECURITY.md](SECURITY.md), not as public issues.

## Repository layout

```text
apps/web/                 SvelteKit application, migrations, deployment scripts
  src/lib/server/         Server-only code, one folder per domain
  src/lib/                Client code, one folder per feature
  migrations/             SQL generated by drizzle-kit, applied when the app starts
  scripts/                Container health check
  tests/                  Tests that read repository files (Compose, Dockerfiles)
workers/inference/        Python worker
  src/anysub_worker/      Worker package
  tests/                  pytest suite
packages/contracts/       JSON Schema and the TypeScript generated from it
docs/                     User and contributor documentation
compose.yaml              Production stack, pulls the published images
compose.cuda.yaml         NVIDIA overlay
compose.build.yaml        Builds the production images from the checkout
compose.dev.yaml          Development overlay
```

Server domain folders in `apps/web/src/lib/server/`: `auth`, `db`, `http`, `jobs`, `media`, `models`, `projects`, `settings`, `storage`, `subtitles`, `transcription`, `uploads`, `workers`.

Worker routes under `/api/internal` check the worker token twice on purpose: once in the `handle` hook and again in each route. Keep both, so a route stays protected if the hook's path match ever changes.

Client folders in `apps/web/src/lib/`: `shared` (code used by server and client), `browser`, `library`, `studio`, `editor`, `timeline`, `admin`, `components`.

Pages under `/admin` are for the administrator only. Each page load and each form action calls `requireAdminOrLogin`, because SvelteKit runs form actions without the layout load.

Worker modules in `anysub_worker`: `models` (the Pydantic protocol), `config`, `cli`, `adapter`, `registry`, `hardware`, `threads`, `protocol_schema`, `errors`, `retry`, `timing`, `progress`, `execution`, `runner`, `client`, `uploads`, `model_cache`, `options` for the option types adapters share, `workspace`, `media/` for FFmpeg-based preparation, `transcripts/` for turning timed segments into subtitles, `remote/` for transcription with external providers, and `adapters/whisperx/` for the built-in adapter.

## Naming and structure

- In the web package, files and folders are kebab-case. Svelte components are `PascalCase.svelte` and rune modules are `*.svelte.ts`. Python modules in the worker are snake_case.
- Do not repeat the folder name in the file name: `media/finalize.ts`, not `media/media-finalize.ts`.
- No barrel files. Import from the module that defines the symbol.
- Web tests sit next to their module. Use `*.test.ts` for unit tests and `*.db.test.ts` for tests that seed and inspect database rows. Worker tests live in `workers/inference/tests/` as `test_*.py`, and the test-only fake adapter is `tests/fakes.py`.
- Use `T[]`, not `Array<T>`, and `type` over `interface`.
- Names say what something is. No cryptic abbreviations.

## Comments and file length

Comment only what the code cannot say: a hidden invariant, a non-obvious reason, an external constraint. Do not restate a name, describe an obvious body, or point at callers. Express intent through names, types, and structure.

Keep files under 500 lines and split a module before it gets there. Keep dependencies minimal, validate user input, and never commit secrets.

In `apps/web/package.json`, add new packages to `devDependencies`. The build bundles them into the server, and the production image installs only `dependencies`, which holds native modules such as `better-sqlite3` that cannot be bundled.

## Toolchain

Everything runs in containers, so none of these need to be on your host. Each version has one source file. Where image tags or CI settings repeat it, a test keeps the copies equal:

| Tool   | Version | Declared in                                                          |
| ------ | ------- | -------------------------------------------------------------------- |
| Node   | 24.22.2 | `.node-version`, `FROM` in `apps/web/Dockerfile`                     |
| pnpm   | 11.15.0 | `packageManager` in `package.json`                                   |
| Python | 3.12.11 | `workers/inference/.python-version`, `FROM` in the worker Dockerfile |
| uv     | 0.11.25 | `FROM ghcr.io/astral-sh/uv` in the worker Dockerfile, `ci.yml`       |

Image tags stay literal in the Dockerfiles and Compose files so Dependabot can update them. A test fails when they drift from the version files. Dependabot bumps only the image tag, so finish an image bump PR by updating the paired file the failing version test names.

## Development stack

```sh
make          # list targets
make dev      # start the stack with the source mounted
make down     # stop it and keep its data
```

`make dev` runs the Compose project `anysub-dev` on `http://localhost:5174`. Set `ANYSUB_DEV_PORT` in `.env` to change the port. Sign-in follows it. The project has its own database, app data, model cache, and `node_modules` volumes, so it never touches a production `anysub` stack on port 5173. It needs no `.env`.

With Podman, add `COMPOSE_ENGINE='podman compose'` to any target and set `PODMAN_COMPOSE_PROVIDER` as described in [docs/INSTALL.md](docs/INSTALL.md#podman). `make -n <target>` prints the commands a target would run.

For a single command in a throwaway container:

```sh
docker compose -f compose.yaml -f compose.dev.yaml -p anysub-dev run --rm --no-deps worker uv run pytest tests/test_retry.py
```

The development worker installs the `speech` and `cpu` extras on start. After changing worker dependencies, rebuild it with `docker compose -f compose.yaml -f compose.dev.yaml -p anysub-dev up -d --build worker`.

## Checks

Run this before you push:

```sh
make verify
```

It runs `check`, `test`, `lint`, `format-check`, and `build`:

- `check`: svelte-check and `tsc` for the web app and contracts, and pyright for the worker.
- `test`: Vitest and pytest, including the database tests and the contract and migration drift checks.
- `lint`: ruff on the worker.
- `format-check`: Prettier for the repository, and `ruff format --check` for the worker.
- `build`: the production web bundle.

CI runs the same checks with a frozen lockfile. The worker checks run without the `speech` and accelerator extras, as in CI, in a venv separate from the one the development worker uses. CI adds one job that builds both production images without pushing them. No `make` target builds production images, so a Dockerfile change is only fully checked in CI. Another job fails on known high or critical vulnerabilities in the web and worker dependencies, and it blocks releases too. To accept an advisory that does not affect Anysub, add its GHSA ID under `auditConfig` in `pnpm-workspace.yaml`, or a worker advisory ID to the `ignored` list in the pip-audit step of `ci.yml`, with the reason.

## UI checks

```sh
make dev       # in one terminal
make ui-check  # in another
```

`make ui-check` signs in to the running dev stack with the dev account (override with `UI_CHECK_EMAIL` and `UI_CHECK_PASSWORD`), screenshots every screen in light and dark at 390, 1024 and 1440 px, and runs axe-core. Screenshots land in `ui-check-output/`, which Git ignores. Serious or critical violations fail the target. It is not part of `make verify`. The Playwright image tag in `compose.dev.yaml` must equal the `playwright` version in `apps/web/package.json`, and a test checks that. It also walks the keyboard paths of the menus, dialogs, toolbars, pane separator and timeline, and checks the theme toggle. A screen that fails to load, redirects elsewhere or scrolls horizontally fails the run.

## Contracts

The Pydantic models in `workers/inference/src/anysub_worker/models.py` are the source of truth for the worker protocol. After changing them:

```sh
make generate
```

This writes `packages/contracts/schema/protocol.schema.json`, then the TypeScript types and validators in `packages/contracts/src/generated`. Commit the schema and the generated files together with the model change. The drift tests fail when they disagree with the models. Never edit generated files. Change the models or the generator in `packages/contracts/scripts/generate.mjs` instead.

## Database

Anysub stores everything in one SQLite database through Drizzle ORM. The schema lives in `apps/web/src/lib/server/db/schema.ts` and, for the authentication tables, `apps/web/src/lib/server/auth/schema.ts`. After changing either:

```sh
make db-generate
```

This writes a new SQL migration with drizzle-kit into `apps/web/migrations`. Review it and commit it with the schema change. Never edit a generated migration. A test fails when the schema has changes that no migration covers. The application applies pending migrations when it starts, with foreign keys off so a table that drizzle-kit rebuilds keeps the rows that point at it, and checks every reference before it serves requests.

A change to existing data, such as filling a new column, goes in a migration of its own:

```sh
make db-generate ARGS="--custom --name=describe_the_change"
```

drizzle-kit creates an empty SQL file for you to write the statements into.

Transactions run synchronously through `withTransaction` in `apps/web/src/lib/server/db/transaction.ts`. Because one cannot interleave with another request, the code needs no row or advisory locks. Do file work before or after a transaction, never inside it, and use `withKeyedLock` when several async steps for one job or upload must not overlap.

Every test file gets its own in-memory database, migrated from scratch. Files named `*.db.test.ts` also clear every table after each test, so they can seed rows freely.

## Releases

The web and worker images share one version, kept in `apps/web/package.json`, `workers/inference/pyproject.toml`, and the image tags in the Compose files. A test fails when they disagree. [docs/RELEASING.md](docs/RELEASING.md) has the steps.

## Commits

Use [Conventional Commits](https://www.conventionalcommits.org): a short single-line message with a type prefix such as `feat`, `fix`, `docs`, `chore`, `build`, `ci`, or `test`. Keep one concern per commit. Update the documentation in the same change as any user-facing behaviour.
